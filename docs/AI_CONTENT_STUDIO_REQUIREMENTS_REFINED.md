# AI Content Studio 需求文档（边界澄清版）

> 文档状态：需求澄清稿，尚未进入实现
> 日期：2026-09-22

## 1. 产品定位

AI Content Studio 不是社媒采集系统，也不是 YouTube 搬运工具。

它接收上游社媒采集系统提供的候选内容和结构化信息，完成从“选中的题目”到“可供人工确认的多平台内容”的自动化生产：

```text
上游候选内容
  → 人工选题
  → 主题理解与主文案生成
  → 按平台特征重构
  → 安全/敏感词校验
  → 平台排版
  → 按平台交付
  → 人工最终校验
```

人的主要工作只有两处：

1. 从候选内容中选择要做的题目；
2. 对排版后的最终内容做发布前校验。

系统负责其余可自动化环节，并保留人工修改、退回和重新生成能力。

## 2. 系统边界

### 2.1 上游系统负责

- 采集社交媒体及其他外部来源的数据；
- 保存原始内容、来源平台、作者、发布时间、链接、互动数据等；
- 对候选内容做去重、基础清洗和可用性标记；
- 通过 API、Webhook 或稳定的数据服务向本系统提供候选内容。

### 2.2 AI Content Studio 负责

- 展示和筛选候选内容；
- 创建和管理选题；
- 生成一份与来源事实对应的主文案；
- 针对不同自媒体平台重构内容，而不是简单复制；
- 执行安全敏感词和平台规则校验；
- 生成平台化排版结果和预发布包；
- 提供人工确认、修改、退回、重生成和版本追踪；
- 保存生成过程、规则版本、模板版本和来源链路。

### 2.3 明确不属于本期

- 社媒平台爬虫和采集调度；
- 直接读取上游数据库；
- 抖音、小红书等尚未接入的平台的自动发布；
- 任何平台的公开发布动作（本期只允许写入公众号草稿箱）；
- TTS、真人口播、视频剪辑和视频渲染；
- 自动判断某段外部内容是否取得法律授权；
- 让 Agent 在无人选择的情况下自行决定选题并发布。

## 3. 目标用户和工作方式

### 3.1 操作角色

| 角色 | 主要动作 |
|---|---|
| 内容运营者 | 选择题目、查看生成结果、最终校验、确认预发布 |
| 系统 | 批量生成、平台重构、校验、排版、生成预发布包 |
| 上游采集系统 | 提供候选内容和来源信息 |

当前按“个人/小团队内部工作台”规划，不把多租户、计费和客户自助配置纳入本期；如果后续确认要对外售卖，需要单独增加租户隔离、账号体系、配额和计费需求。

### 3.2 目标工作流

```text
候选池
  → 选择一个或多个题目
  → 批量生成多平台草稿
  → 自动安全校验
  → 自动排版
  → 运营者集中检查
  → 按平台进入草稿箱或可复制交付状态
```

运营者不需要逐条重新写稿，但必须能够编辑和覆盖系统结果。

## 4. 上游输入契约

本系统至少需要从上游获得以下字段：

| 字段 | 必需 | 用途 |
|---|---:|---|
| `external_item_id` | 是 | 幂等和追溯 |
| `source_platform` | 是 | 来源展示和平台语境 |
| `source_url` | 建议 | 回溯原文 |
| `title` | 是 | 候选题目和初始标题 |
| `content_text` 或 `transcript` | 是 | 主题理解和生成输入 |
| `author` | 否 | 来源说明 |
| `published_at` | 否 | 时效判断 |
| `engagement_metrics` | 否 | 选题参考和后续反馈 |
| `tags` | 否 | 筛选和分类 |
| `provenance` | 建议 | 来源类型、采集时间、处理状态 |

接入方式优先使用 API/Webhook/稳定数据服务；禁止通过共享数据库表耦合。

## 5. 功能需求

### 5.1 候选内容池

- 接收上游候选内容；
- 按来源平台、时间、标签、互动指标和处理状态筛选；
- 展示标题、摘要、来源、原文链接和可用素材；
- 标记“未选题、已选题、生成中、已完成、已归档”；
- 同一个 `external_item_id` 重复推送时必须幂等，不重复创建候选内容；
- 记录上游数据快照，后续生成不能因上游内容变化而悄悄改变。

### 5.2 选题中心

- 运营者可以从候选池创建选题；
- 一个选题可以绑定一个或多个候选内容；
- 选题需要记录：主题、目标受众、核心角度、期望平台、禁用表达、补充说明；
- 选题创建后可启动一次多平台生产任务；
- 允许取消、重试和重新生成，但不能覆盖历史版本；
- 系统可以提供排序或推荐，但不能绕过运营者直接进入生产。

### 5.3 主文案生成

系统先生成一份平台无关的主文案或内容事实骨架，至少包括：

- 主题和核心结论；
- 内容摘要；
- 关键事实和来源引用；
- 叙事顺序；
- 可能的风险表达；
- 可供平台重构使用的段落或信息单元。

主文案必须保存使用的来源快照、模型、提示词和版本信息。

### 5.4 多平台重构

平台重构不是简单截断或替换标题，而是依据平台特征重新组织内容。

首期沿用现有产品的三个目标渠道：抖音、小红书、微信公众号。渠道必须采用可配置模板，后续可以增加平台。

#### 抖音

- 强开头/Hook；
- 口播脚本；
- 分段或分镜提示；
- 屏幕文字；
- 结尾互动或行动引导；
- 目标时长和字数约束。

#### 小红书

- 多个候选标题；
- 首屏摘要；
- 分段正文；
- 话题标签；
- 封面文案；
- 适合图文阅读的段落结构。

#### 微信公众号

- 标题和摘要；
- 完整长文结构；
- 小标题、引用、列表和强调排版；
- Markdown/HTML 等可预发布格式。

每个平台生成独立草稿；一个平台失败不能覆盖或回滚其他平台的结果。

### 5.5 安全与敏感词校验

安全校验必须在预发布前自动执行，并且不能被人工“直接跳过”。

至少支持：

- 敏感词、禁用词和短语匹配；
- 正则或规则匹配；
- 平台特定风险词；
- 夸大、绝对化、保证性表述；
- 需要人工确认的风险表达；
- 命中位置、命中规则、严重程度和修改建议；
- 规则版本记录。

结果分为：

```text
pass       可进入预发布
warning    可进入人工校验，但必须展示原因
blocker    不得进入预发布，必须修改后重新校验
```

安全规则与平台模板都必须版本化，避免历史稿件因规则更新而被无记录地改写。

### 5.6 排版

- 根据平台模板自动生成最终结构；
- 生成前端可预览的排版结果；
- 支持人工修改标题、段落、标签、CTA 和格式；
- 保存“生成版本”和“人工修改版本”；
- 每次修改都产生新的 revision，不覆盖历史内容；
- 排版失败必须显示明确原因，不得静默输出半成品。

### 5.7 预发布

本期“预发布”按平台采用两种交付方式：

| 平台 | 自动交付方式 | 人工动作 |
|---|---|---|
| 微信公众号 | 通过现有 `publish_wechat` 能力写入官方草稿箱 | 在公众号后台检查草稿，确认后自行公开发布 |
| 抖音、小红书及其他未接入平台 | 生成已排版、可复制/导出的发布内容 | 复制粘贴到对应平台并完成发布 |

公众号写入草稿箱也不等同于公开发布。必须经过本系统的安全校验和运营者最终确认后，才允许调用草稿箱投递。

每个平台的交付结果至少包括：

- 目标平台；
- 最终标题/正文/脚本；
- 排版结果；
- 来源和生成版本；
- 安全校验结果；
- 需要人工确认的提示；
- 预览和复制/导出内容；
- 若为公众号草稿箱投递，保存投递结果和平台返回的 `media_id`。

只有满足以下条件，状态才可以进入平台交付阶段：

- 生成任务完成；
- 平台格式校验通过；
- 不存在未解决的安全 blocker；
- 来源和版本信息完整。

运营者完成检查后：

- 公众号调用草稿箱投递能力，成功后进入 `published_to_draft_box`；
- 其他平台进入 `ready_for_manual_publish`，供人工复制粘贴发布。

实际公开发布接口仍不属于本期。

## 6. 状态和版本

### 6.1 选题状态

```text
candidate
selected
generating
generated
in_review
approved
archived
```

### 6.2 平台草稿状态

```text
queued
generating
generated
safety_failed
format_failed
ready_for_pre_publish
changes_requested
approved_for_publish
published_to_draft_box
ready_for_manual_publish
delivery_failed
archived
```

### 6.3 不可变信息

每个草稿版本必须保存：

- 上游候选内容快照；
- 选题版本；
- 平台和模板版本；
- 安全规则版本；
- 模型和提示词版本；
- 原始模型输出；
- 人工修改记录；
- 校验结果和时间。

历史版本只能查看和复制，不能被新生成结果覆盖。

## 7. 自动化要求

- 选题确认后，可一次性触发多个平台生成；
- 生成、校验、排版应支持异步任务；
- 单个平台失败可以单独重试；
- 重试不能生成重复的预发布包；
- 批量任务需要显示整体进度和每个平台状态；
- 系统应在人工检查前集中展示所有 warning 和 blocker；
- 运营者确认后，公众号自动写入草稿箱；
- 对未接入自动发布的平台，系统自动生成最终排版内容、复制文本和导出文件；
- 人工只在选题选择和最终校验处介入，其他步骤默认自动执行。

## 8. 质量和验收标准

### 8.1 主链路验收

1. 上游推送一批候选内容；
2. 系统完成幂等接收并展示候选池；
3. 运营者选择一个题目；
4. 系统生成主文案；
5. 系统分别生成抖音、小红书、公众号版本；
6. 三个版本分别完成安全校验和平台排版；
7. 命中 blocker 的版本不能进入预发布；
8. 无 blocker 的版本进入平台交付阶段；
9. 运营者可以集中查看、修改和批准；
10. 公众号版本自动写入草稿箱并保存 `media_id`；
11. 抖音、小红书版本生成可复制粘贴的最终排版结果；
12. 全流程可追溯到上游内容和规则/模板版本。

### 8.2 不能直接采用的示例数字

对话中的“AI 完成 80%～90%”“13 分钟/条”“每天测试 20 条”等只能作为后续运营评估假设，不能直接写成开发验收指标。正式指标需要基于真实运行数据另行确定。

## 9. 与现有 AI Content Studio PRD 的关系

现有 PRD 中的 FactPack、版本化 Draft、渠道模板、事实校验、审核和导出能力可以复用，但需要调整边界：

1. Source/Connector 的主职责从“本系统采集多种来源”调整为“接收上游采集系统的候选内容”；
2. Topic Center 保留并成为本产品的核心入口；
3. Generate 扩展为“主文案生成 + 平台重构”；
4. Fact Checker 之外新增独立的安全敏感词校验层；
5. Review/Export 调整为“平台交付”：公众号进入草稿箱，其他渠道输出可复制内容；
6. 复用现有 `publish_wechat` 草稿箱能力；
7. TTS、视频剪辑和任何平台的公开发布不纳入本期主链路。

## 10. 待确认项

- 上游系统最终采用 API、Webhook 还是定时拉取；
- 安全规则由谁维护，以及是否需要每个平台独立规则集；
- 公众号草稿箱凭据和封面素材的运行时配置方式。

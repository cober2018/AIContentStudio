# 第三方写作的图文检查由第三方模型执行

## Why
图文的「事实检查」（graphic_fact）和「身份检查」（graphic_identity）是 AI 复核，现在不管谁写稿，都固定调用平台设置里登记的模型（gemini-3.8-flash-high）。
- 用户的意思是：写作方式选「第三方模型」时，检查也应该由第三方模型来做；选「平台模型」时，继续用平台配置的模型。
- 第三方模型只通过 MCP 操作平台，平台服务器没有它的接口，不能直接调用。
- 阿军这篇（候选 15）的两条提醒，就是平台模型调用失败留下的，原因不可查（已加日志，本次未复现）。

## What Changes
1. **写作方式决定复核方**：
   - 写作方式为「平台模型」：沿用现有行为，调用平台配置的模型。
   - 写作方式为「第三方模型」：平台不直接调用模型，把复核请求挂起，等第三方模型通过 MCP 领取并交回结果。
2. **MCP 领取与提交**：新增两个 MCP 工具（沿用现有 creative MCP 的鉴权）：
   - 领取：返回待复核的图文正文、事实清单（只含已通过模型可用检查的条目）、身份规则。
   - 提交：第三方模型按现有输出格式（issues 列表，severity、span、reason）回传；平台校验格式后写入检查结果，并记录提交方的模型标识。
3. **检查结果**：提交通过格式校验后，检查记为 pass 或 warning（有 issue 时），coverage 标明 semantic=verified，provider 写为第三方模型，而不是 gemini。
4. **未提交**：第三方模式下复核未提交前，检查保持「等待第三方复核」，不记为通过；作品不能冻结候选。
5. **不改**：平台模式的代码路径；不改图片视觉复核（identity 的 visual_semantics 仍为不可用，仍是警告）；不把第三方提交当作审批，批准仍由用户点。

## 已定（2026-11-09 用户确认）
- 文字作品一起改：text_master_checks 的事实、身份复核同样走第三方。
- 第三方未提交时卡住冻结：复核结果为「等待第三方复核」，检查记为未完成，候选不能冻结。

## 不做
- 不让平台替第三方模型调用它的接口。
- 不在第三方模式下自动回落到 gemini。
- 不改写作流程（稿子仍由第三方模型写）。

## 验收
- 写作方式为第三方模型的图文，平台不调用 gemini；事实/身份检查停在「等待第三方复核」。
- 第三方模型通过 MCP 领取并提交后，检查出现第三方模型标识，并写入 coverage.semantic=verified。
- 写作方式为平台模型的图文，行为与现在一致。
- 提交格式错误时，检查记为失败并给出具体原因，不记为通过。

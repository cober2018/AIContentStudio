## Context

PRD §3、§6、§15–16 定义抖音脚本、小红书图文、公众号长文为 V1 三渠道及其发布门槛。旧链路已支持三渠道生成和格式导出；归档的 M1 变更建立了冻结证据、母稿、候选审批、素材哈希、独立交付目标与人工回执，但只允许公众号和 X Thread。此设计将 PRD 三渠道拉到同一交付语义。

## Goals / Non-Goals

**Goals:** 复用现有证据/审批/交付对象，使抖音脚本和小红书图文可预览、批准、下载完整包、按账号人工交付并回填；保持旧三渠道稿件可读；能逐项对照 PRD 验收。

**Non-Goals:** 生成视频成片、TTS/真实时间轴、抖音或小红书平台 API 发布、全渠道扩展、商业多租户，以及仅凭本变更宣布完整 V1 上线。

## Decisions

1. **PRD 优先级。** `03_ai_content_studio_PRD.md` 是长期目标，`docs/AI_CONTENT_STUDIO_V1_ALIGNMENT_PLAN.md` 是后续扩展规划。先补 PRD 明列的三渠道，再按独立变更扩更多平台。既有 X Thread 能力保留。
2. **共用受控交付主链。** 扩展 `article_handoff` 的频道/内容形态规则、候选快照与 `DeliveryTarget` 枚举约束；不要另建一套抖音/小红书审核和回执表。旧稿若无完整证据、候选哈希和素材快照，保持 legacy 可读但不伪装为已批准可交付。
3. **渠道成品定义。** 抖音输出结构化脚本、场景、字幕文本、B-roll 提示和估算 SRT，包内明确“仅脚本”。小红书图文必须有有序图片实际字节、正文、标题与标签；图片 Prompt 只作辅助，不算成品图片。图片可来自已获公开使用许可的上传素材或确定性模板渲染；不强制调用生图服务。
4. **同一批准快照。** 候选哈希覆盖正文、频道结构、引用、实际素材顺序与哈希、声明和检查结果。任何修改生成新候选并使旧派生包失效；撤销公开使用权限阻止未完成目标继续交付，历史审批记录仍保留。
5. **交付状态准确。** 包就绪、人工确认、真实平台已发布分别记录；人工回填不能自动变成平台公开发布证明。目标账号权限复用 M1 授权检查。

## Risks / Trade-offs

- [旧三渠道 Draft 与新候选结构不同] → 逐条标记为历史未补验，仅在新候选完整批准后允许目标创建。
- [小红书图片顺序与批准内容漂移] → 将顺序和字节哈希纳入 manifest，打包时重读并核对。
- [抖音 SRT 被误当真实音频字幕] → 包内显著标记 estimated，并保留原有估算逻辑。
- [数据库渠道约束拦截新目标] → 使用显式迁移扩约束，分别验证 SQLite 和 PostgreSQL；不重写旧行。

## Migration Plan

先新增兼容性迁移和读取路径，再开放新目标写入与前端入口；迁移前保留数据库备份。若需回退入口，禁用新渠道目标创建并保留已写行以便恢复读取，不通过删除历史目标回滚。

## Open Questions

没有阻碍此提案的产品决策。真实账号人工发布和 PRD 30 个真实 Topic 的验收需在实现后用用户素材执行，结果单独记录。

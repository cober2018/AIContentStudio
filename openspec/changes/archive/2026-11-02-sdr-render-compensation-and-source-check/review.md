| 项 | 结论 |

## 缺陷：原片取帧时刻不对

- 位置：`apps/api/app/services/delivery_checks.py` `_source_ms()`。
- 原因：导演稿 `timeline` 的画面轨条目只有 `shot_id / start_ms / end_ms`，没有 `material_revision_id` 和 `trim_start_ms`，所以总是走兜底 `mid - shot["start_ms"]`，等于假定每个镜头从素材第 0 秒开始用。实际镜头大多从素材中间截取。
- 证据（项目 48 / 作品 93 任务 42 成片，同一个 `_frame` 读数）：

| 镜头 | 平台取的原片时刻 → 亮度 | 实际用到的时刻 → 亮度 | 成片亮度 |
|---|---|---|---|
| shot-0 | 0.25 s → 135.0 | 1.15 s → 141.1 | 141.0 |
| shot-1 | 2.85 s → 138.9 | 3.55 s → 136.3 | 135.6 |
| shot-6 | 0.85 s → 137.4 | 8.55 s → 146.8 | 145.3 |

- 影响：按正确时刻，任务 42 各镜差 0–1.5 级；按现在的时刻，shot-6 差 +7.9，离提示线 8 只差 0.1。画面变化大的素材会误报，或掩盖真的压暗。
- 修法建议：按剪辑清单 `timeline[].trim_start_ms`（有 `speed_percent` 时按变速换算）取原片时刻。剪辑清单在成片之后交，可以在清单交上来时补算，并更新成片输出的 `shot_checks` 提示。

## 缺陷（2026-11-03 复核新发现）：补偿 LUT 把亮部压暗了 5–10 级

原先作为「描述不一致」的可选建议。用户指出颜色错了每次都要返工，复核后确认不只是描述问题，LUT 本身也要改。用户已确认要改。

- 位置：`craft_skills/craft-resolve/luts/sdr-render-comp.cube`。这份 LUT 是审计方在任务 42 做的，开发方原样收进了仓库。
- 现状：LUT 在输入 0.8（204/255）以下是 +20；0.8 以上柔和压到 1.0。但实拍片段渲染后整体还会再 −19，一直到最亮都是这样（任务 41 未补偿：原片 225–239 → 成片 −19）。所以亮部被压了两次。
- 证据：任务 42 成片 4 个自拍镜头（shot-0/1/2/6），在原片同一时刻逐像素按亮度分段比较：

| 原片亮度段 | 成片和原片差 |
|---|---|
| 0–209 | 0 ～ +1 |
| 210–224 | −5 |
| 225–239 | −10 |

- 影响：210–239 这一段约占画面两成，是白墙、**商品包装盒**、白衣服和鼻尖高光（标注图：同目录 `highlight-band-210-239.png`，左 shot-0、右 shot-6，白色就是这一段）。商品是视频的主角，包装盒发暗。平台检查和审计方的验收都只比平均亮度（差 ≤2），所以没发现。
- 要求（按结果验收）：
  - 原片 0–235 的每个亮度段，成片和原片差 ≤2 级。
  - 实拍片段渲染后最亮只能到约 236。原片高于 236 的部分做不到一样，可以只在最顶上一小段做压缩来保留层次。这一限制要写进 color.md。
  - 如果能查出造成 −20 的项目或渲染设置、从根上解决，就按 color.md 里「从根上解决」那条走，不再需要补偿 LUT。
- 做法建议（开发定）：把柔和压缩的起点从 0.8 提到约 0.88（225/255），也就是 225 以下严格 +20，225–255 压进 245–255。改完用任务 42 的 4 个自拍镜头按上表重比一遍。
- color.md 要同步：
  - 第 50 行「整体 +0.078」改成实际曲线。
  - 「检查」那条除了比平均亮度，还要分段比亮部，至少看原片 200 以上的区域，比如墙和白色包装。

## 要加（用户 2026-11-03 确认）：成片对比原片亮度，亮部也要比

- 位置：`apps/api/app/services/delivery_checks.py` `source_brightness`（以及剪辑清单补算 `recheck_sources`）。
- 为什么：现在每个镜头只比一帧的平均亮度。上面那个 LUT 缺陷让任务 42 的白墙和包装盒暗了 5–10 级，但平均只差 0.1–1.7 级，提示线是 8，检查完全抓不到。
- 怎么比：比两帧的亮度分布，不逐像素比。平台不知道镜头有没有翻转、裁切，也不知道叠层盖在哪，对不齐像素；分布比不受这些影响。审计方上面那张分段表是手工翻转对齐后算的，平台做不到。
- 实测（平台同样的取帧：每镜中点、宽 160、灰度全范围；原片按剪辑清单时刻）：

| | 平均差 | 亮部 P90 差（亮度排在九成位置的那个值） | 最亮两成的平均差 |
|---|---|---|---|
| 任务 41（未补偿） | −15.9 ～ −18.9 | −18 ～ −19 | −15.6 ～ −18.9 |
| 任务 42（当前 LUT） | −0.1 ～ −1.7 | −6 ～ −7 | −5.3 ～ −6.8 |

- 要求（按结果验收）：
  - 每个参与原片对比的镜头（范围和现在一样，HLG/PQ 原片不比），在平均亮度之外再比亮部。差超过亮部提示线就在审阅页提示「第 X 镜亮部比原片暗/亮 N 级（成片 …，原片 …）」，提示带上取帧依据（清单 / 交付时报的 / 估计）。
  - 亮部提示线和现有提示线一样放在阈值配置里，可调。建议用 P90，提示线 5 级；开发可以换别的量法，但要满足下面的验收。
  - 剪辑清单交上来补算时，亮部也按清单时刻重算并替换提示。成片的亮部读数要随每镜读数存下来，精简形式（`[shot_id, luma, lufs, source_luma]`）也要带上，否则补算时拿不到。
- 验收：
  - 任务 41 成片：4 个自拍镜头都报亮部暗约 18–19 级。
  - 任务 42 成片：4 个自拍镜头都报亮部暗约 6–7 级，平均亮度照旧不报。
  - LUT 按上面缺陷改好后重新渲染的版本：亮部和平均都不报。
- 已知限制：大块白色或亮色叠层盖住的镜头，成片亮部会被叠层抬高，读数可能偏亮。作为已知限制写进规则说明就行，不用为此做遮罩。

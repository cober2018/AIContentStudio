## Context

当前 daily_opportunities.py 的 hot/recent_report 均受48小时证据窗口限制；evergreen 已存在但依赖候选先正确分类。_collect_articles 还受20项尝试、12KB输入限制，不能将未纳入分析的线索说成已评估。OpportunityPages 默认台北当天+recommended_only，旧建议被日期隐藏，空态仅说明没有符合条件内容。

科技角色2绑定AIHOT source54，生活角色3绑定source55；discovery_aggregation.source_id_for/accepts_source 当前偏向单一聚合源。Radar 接入必须将科技的明确允许源集合扩为主源+补充源，不能取消分流检查或重新打开所有旧信源。

## Goals / Non-Goals

目标：科技价值分类、有效建议可见、执行原因可解释、Radar可追溯补充发现。2026-10-19已获用户授权，规格复核后进入apply。

非目标：修改生活选题时效、替换AIHOT、SEO/GEO内容生产、无限追溯/模型补跑、改变调度、自动创建项目、公开发布。2026-10-19补充授权允许安装并运行Radar免费信号；不新增凭据或付费服务。

## Decisions

### 0. 已授权的自动日报补充（2026-10-19）
用户确认将日报生成接入既有调度。采用现有catchup step在科技日批hour（当前08:00、Asia/Taipei）之后先生成后导入；不增加Beat条目。日粒度SystemSetting回执＋本机文件锁防重复；同日失败/中断unknown不自动重跑，次日只执行当天。固定已安装兄弟目录new-term-radar、已核验commit、Python3.12和免费参数，不接受任意shell命令。最长300秒，Radar来源lease覆盖该上限；报告先写独立当日目录，结构校验后原子替换消费文件，保留旧报告与当日证据。启用字段auto_daily显式可关闭。GET只读。生成失败不复用旧文件冒充今日，来源partial仍不阻断AIHOT；不更改生活调度、选题预算或调用付费模块。安装仓库更新需重新核验，不能自动git pull。

### 1. 科技专属版本化策略

明确策略绑定科技Persona，而非根据名字模糊匹配；其他角色继续既有策略。沿用 hot/recent_report/evergreen 三类存储语义，科技显示为最新动态/近期进展/深度常青。

- hot：48小时内可证实质事件；观测热度仍按原48小时/24小时半衰期计算。
- recent_report：最近30天的可证原文报道或实质技术更新。不可用抓取、转载、发现时间刷新年龄。
- evergreen：无统一来源年龄淘汰线，必须解释持久技术价值并通过正文和评分门槛。涉及当前版本、接口、价格、可用性等不能从旧材料推断；未核实则删去当前性主张或暂缓该候选。
- 分类在同一候选生成阶段明确执行，过48小时仅失去hot资格，不直接失去参评资格。日期未知不能作hot/recent_report；只有能证明持久价值且不依赖未知当前事实时才能成为evergreen，不能机械换标签。
- 保留30/25/20/15/10权重、双次独立评分、平均70与两次证据分70。时效分随类型解释，非热点不因年龄单独硬淘汰。维持每日最多5条、同来源主体最多2条、最终最多10候选及原预算。

排除方案：统一改7天仍然混淆新闻和工程价值；完全去掉时效会把旧发布当新消息。

### 2. 原文年龄与建议有效期分离

新科技建议有效期采用确定性类型默认：hot48小时、recent_report7天、evergreen30天，从生成时间计算并写入relevant_until；原文日期不改。用户已有决定和旧行不回填、不自动延长。旧记录缺有效期时在历史视图显示“有效期未记录”，不隐式永久有效。

科技默认查询 persona + status in(new,qualified) + relevant_until>now，不限制生成日。显式“今天新生成”才附加Asia/Taipei日期。历史视图仍可看过期、已处理和缺有效期记录。Home科技建议同样排除过期；生活默认日期和生命周期不变。下一批采集不能仅因建议过期重复写相同角色/事件/角度。

### 3. 真实诊断，不伪装成全量评估

复用研究Run现有input/output JSON保存版本化诊断，无新运行真源。分离采集项、正文读取成功/失败、预算未分析、候选生成数、证据/类型淘汰、进入评分数、评分淘汰、去重/主体限制、已保存数。各阶段明确计数单位；每个候选每阶段最多一个主要退出原因，辅助原因不重复相加。历史缺字段返回null/未记录，不推算为0。

无当天run、运行中、waiting_collection、blocked/failed/unknown、真实完成零结果、筛选隐藏分别呈现。显示所选角色、所选业务日及最近批次实际日期，不能用昨天失败解释今天尚未执行。保留可用机会同时显示partial来源缺口。详情提供已记录的候选理由和原文入口，安全错误码代替原始Provider响应。页面刷新不触发采集、模型或重试。

### 4. Radar是输入适配，不是第二套选题系统

参考 https://github.com/zhuyansen/new-term-radar 及README.zh-CN（2026-10-19读取）。它是需配置的雷达软件，不是该GitHub URL本身持续提供的新闻feed；当前未验证本机实例、固定API或报告路径。

实施先检查可用输出及版本，优先只读消费用户已有结构化报告/导出；其次验证有文档的只读接口。不臆造REST端点，不抓取仓库README当雷达日报。若均无可用输出，保持未配置并报告最小运行方案；新安装、付费模块或凭据需要另行确认。此准备工作不能被标为端到端接入成功。

适配器输出本系统规范化字段：producer/version、upstream_item_id（或规范URL稳定hash）、title/term、original_url、discovered_at、observed_at、可证published_at/event_at或null、signal_kind、payload_hash、原始溯源。字段是本地契约，不声称上游原生提供。重复导入不增条，变化追加版本；历史报告重读不刷新发现时间。仅扫描配置目录内明确文件或允许端点，复用现有URL安全和正文抓取限制，远端内容是数据不是可执行指令。

已核验0.4.0 daily JSON：适配器消费明确绝对路径的report，保存时需确认实际producer版本；获补充授权后在独立仓库运行免费GitHub/Hugging Face信号，报告生成与应用只读导入分开。日报格式没有完整时间区间水位与撤回协议，因此文件读完不等于停机区间覆盖完成，补采保留partial/unknown interval；日报缺项不自动撤回历史线索，显式停用/撤选仍生效。

复用DiscoverySource/Item/订阅，科技允许源集合={其现有AIHOT,明确启用的Radar}；生活不变。合并候选保留两条发现路径，独立来源主体按最终原始发布者计数，不按两个聚合器计数。正文、引文、真实性和撤回规则同AIHOT。上游星数/新词分数只是带时间的观察信号，不能替代本系统评分或证明全网热度。

沿用既有scanner与日批，不新增第二个定时器。Radar部分失败不阻断有证据的AIHOT结果，须显示partial。总正文/模型预算不因增加源自动变大；确定性轮转两个可用源的线索再应用现有上限，记录实际覆盖，不能声称全量分析。

### 5. 与active规格的衔接

add-daily-persona-content-opportunities 的 Event grouping and observed heat 保留；其科技当日默认展示由本包的显式视图契约取代。add-aihot-persona-source-integration 的角色映射与可逆模式保留，科技单源选择扩成显式允许源集合；生活不扩展。新策略以版本记录到run和信号，旧评分及自然日批证据不改。

归档前必须先协调这些尚未canonical的依赖：先同步基础change，再合并本包新增requirement，并对基础change中“页面默认当天”的条款加科技例外，不能把冲突文字同时作为现行规则。若基础change尚未验收，本包可独立评审/实施，但不得自动关闭基础验收或宣称整体归档完成。

## Risks / Trade-offs

- 旧材料容易被说成新事实 → 保留真实日期/版本及证据门槛，不靠改标签放行。
- Radar没有可消费实例 → 明示未配置；模型模拟线索不算真实验收。
- 扩大候选窗口不保证每天有5条 → 记录覆盖与淘汰，不降低评分凑数。
- 正式工作区已有大量修改 → 仅白名单触及本需求文件；规格阶段不动任何已有业务文件。

## Migration Plan

预计复用JSON和现有表，无迁移。实施若证明需要持久结构变更，先修订规格。启用须备份并保留旧策略/源集合；回退恢复科技策略与查询默认，停用Radar订阅，保留所有历史run/来源版本/机会。正式写入和真实模型验收另获授权。当前不重跑历史批次或改cron。

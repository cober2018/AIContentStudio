## Context

FE-F6A–F6D use append-only ContentMasterRevision and Candidate v4. `ContentUnit.channel_id` and Master channel/form columns are nullable, but save/readiness currently treat a Unit's channel as Master context and v4 freezes that context directly. Project Matrix has explicit Unit CRUD; Review/Delivery bind immutable Candidate hashes. The source F6E package calls for a separate post-Master ChannelVariant and Candidate v5. The old V1 deliverables change is already superseded by `align-v1-prd2-content-harness`; its seven acceptance scenarios remain evidence sources, not an active parallel implementation. FE-F6E business-code apply requires F6D gates and a fresh base audit; this change is specification-only until then.

## Goals / Non-Goals

**Goals:** Non-mutating matrix planning; append-only, project-owned ChannelVariant revisions with exact source/profile/adapter/ref lineage; channel-neutral source path; v5 Candidate/Review/Approval/local-package dispatch; truthful controlled registered-form packages and legacy scenario retention.

**Non-Goals:** Auto-creating the matrix Cartesian product; publisher-side rewriting; silently converting old v3/v4 Candidates; unverified remote publication; new Identity or Fact Boundary; reactivating the superseded V1 change or treating its acceptance as complete; production migration.

## Decisions

1. **Matrix is a projection, not a second plan database.** Suggest from current Opportunity/Brief/Identity/Registry/existing Units and coverage-qualified Performance summaries. Bound result size and show reason/unknown/cost data. A user-selected subset creates Units through existing project APIs with their normal authorization and fork/archive rules. A selected channel is a production target, not an FE-F4 DeliveryTarget; Delivery Authorization is permitted only for an approved exact Candidate. No suggestion silently changes Identity, Memory, Project, Unit or delivery authorization. Alternative: durable Cartesian matrix rows; rejected because they duplicate Unit truth and create speculative content.

2. **One variant series per explicit key.** A stable `variant_key` identifies an alternative under a Unit × channel × content_form. Revision numbers and optimistic CAS are scoped to that key; unique `(unit_id, variant_key, revision_no)` and `(unit_id, variant_key, idempotency_key)` prevent race duplicates. Each revision pins source Master ID/payload/context, Unit IdentitySnapshot, exact published profile ID/version/config hash, adapter key/version, `payload_schema`/canonical `payload_json`/`payload_hash`, context hash, source_kind/edit summary, actor, parent and request fingerprint. A key cannot silently switch channel/form or source Unit. The server derives the hash from the adapter-validated canonical schema and payload, never arbitrary adapter JSON. Alternative: mutable latest row; rejected because frozen Candidates need immutable provenance.

3. **Refs and checks are first-class exact records.** New asset/evidence refs point to existing MaterialRevision and FactPackItem, never copied bytes or text. Final refs are explicit even when inherited from Master, with role/order/placement, checksum/rights snapshot and source locator. Checks are append-only, keyed to exact variant input/profile/adapter/rule hashes. Live rights/evidence and current checks are revalidated at freeze, approval, new authorization and package gates as appropriate. Alternative: implicit Master refs; rejected because adaptation can change order or omit assets.

4. **Adapter is replaceable but cannot invent authority.** Versioned `capabilities/validate/adapt/preview/render/required_checks/package_projection` resolve the exact Registry form and published profile. The first executable compatibility matrix is `text.master.v2 → wechat/article, x/thread, x/single`; `graphic.master.v2 → xiaohongshu/image_note`; `video.master.v2 → douyin/spoken_script`. Each adapter declares accepted source schemas and target `artifact_kind` (`text`, `image`, `script` respectively), checks them against the exact published profile and returns typed unavailable/no-write on mismatch. A historical v1 Master must take its F6B/C/D explicit v2 fork before F6E adaptation; no implicit upgrade. Matrix suggestions must use the same executable compatibility result. Deterministic adaptation can propose a concrete payload. Model-assisted adaptation returns a suggestion backed by a successful exact-input `LLMRun`, followed by explicit accept and durable save; unavailable providers fail closed. The save path verifies run purpose/provider/model/prompt version/input hash and accepted canonical output hash against the exact source Master, target profile and adapter. Variant/v5 manifest stores only a safe projection (`llm_run_id`, provider/model/prompt version/purpose, input/accepted-output hashes, status), not `raw_output`, error text or provider secrets. No adapter can repin Identity, add unsupported claims, bypass the frozen Fact Boundary or grant public-use rights. Alternative: publisher-side transformation; rejected because approval must cover final bytes/content.

5. **Channel-neutral is opt-in, not a backfill.** A newly created Unit may intentionally have `channel_id=null`; its Master then has null channel/form and is source-only, not v4 Candidate-ready. Channel-bound Units/Masters remain unchanged and can still use v4. A channel-bound Master may also explicitly source a variant, with its original channel preserved as provenance. Source Master currentness uses the exact Unit context; variant currentness additionally uses its target profile/adapter/rules. No historical row is relabeled neutral.

6. **V5 is a separate Candidate source path.** A pure canonical manifest builder freezes exact Project/Unit/Identity, source Master, ChannelVariant schema/payload/hash, target channel/form/profile, ordered refs/checks/render, citations/declarations and adapter/model provenance. For v5, `ContentAsset.channel_variant_revision_id` is the sole Candidate source pointer; `draft_id`, `topic_brief_id` and `content_master_revision_id` stay null. The source Master is reached through the Variant FK and frozen manifest, not a second Candidate source link. `ContentAsset.channel`, `content_form` and `artifact_kind` are checked projections of the frozen target and exact published profile; all schema-aware readers validate their agreement with the manifest before processing. V3/v4 retain their original source links. Freeze uses CAS/idempotency and checks current Master/variant/context plus live rights and byte hashes. Review/Approval/Delivery/Package dispatch on `schema_version` before touching Draft/v4 fields, enforce the same raw-ID ownership/archive boundary, and never fall back to v4/v3 after a v5 failure. Approved/authorized history stays immutable; unknown delivery remains unknown and requires reconciliation.

7. **Controlled forms reflect actual Registry capability.** F6E includes `wechat/article`, `x/thread`, `x/single`, `xiaohongshu/image_note`, `douyin/spoken_script`, each only after its exact published form/profile and matching adapter are executable. The current seed already registers both X forms; F6E must implement and test both distinct X adapters, rather than deferring single-post support because it is harder. Until each adapter passes its own gates, its form remains unavailable. The legacy `x_thread/thread` fallback has no published profile; its existing v3/v4 behavior remains unchanged, but it is not a v5 target. Registration alone does not imply an adapter or verified remote Publisher. Xiaohongshu requires ordered real image bytes/hash/rights; Douyin script/estimated SRT is labeled script-only, not a finished video or timed audio. Missing/withdrawn bytes block package while preserving the approved Candidate. Package construction performs no remote call.

8. **Superseded V1 acceptance remains an evidence source, not an active implementation change.** `complete-prd-v1-channel-deliverables/.openspec.yaml` already declares `superseded_by: align-v1-prd2-content-harness`. Preserve its seven scenarios and three-channel readiness, Douyin script package, Xiaohongshu ordered images, account-separated authorization/reconciliation and PRD §15/§16 acceptance obligations as named FE-F6E/F7 evidence. A passing local package does not imply 15 criteria or 30 real Topics are accepted. Do not delete or reactivate the superseded change, and do not claim its historical acceptance obligations complete without separate evidence and authorization.

   The seven preserved legacy scenarios map to: old-draft unreadiness → new capability history requirement; approved Douyin script → controlled deliverable; missing image and changed order/bytes → controlled deliverable/ref/manifest gates; separate accounts and revoked rights → v5 delivery/live gates; overall V1 status → explicit PRD acceptance requirement. This mapping is a preservation plan, not a claim that those scenarios already pass.

9. **V5 target channel is not the source Unit channel.** Existing Delivery Authorization checks `ContentUnit.channel_id == payload.channel` for project Candidates. For v5 only, authorization must instead match the Candidate's frozen Variant target channel/form/profile; the Unit channel remains source provenance. Account authorization still checks project/persona and any pinned Unit account. `ContentAccountRevision.profile_json` has no typed channel binding today, so F6E must not infer platform compatibility from free-form profile text: a local package remains a manual handoff, while a remote action fails closed without the exact F7 account/channel/form/action verification. V3/v4 keep their current Unit-channel rule. A cross-channel Variant does not silently repin IdentitySnapshot or authorize a different ContentAccount; if an explicit pinned-account constraint conflicts with the target, the editor must create a separately bound Unit rather than bypass the gate.

10. **Canonical Variant payload is a durable adapter output, not opaque JSON.** Each first-batch schema has a versioned, bounded shape: `wechat.article.v1` has title and ordered stable-ID text blocks; `x.thread.v1` has ordered stable-ID posts; `x.single.v1` has one post text; `xiaohongshu.image_note.v1` has title and ordered stable-ID cards binding exact image-ref keys with captions; `douyin.spoken_script.v1` has ordered stable-ID scenes with script, B-roll ref keys and voice text, plus optional explicitly estimated SRT. All schemas constrain field lengths and list counts by the exact published profile or a stricter adapter limit. Canonicalization normalizes strings, IDs, field presence and array order before hashing; it rejects unknown/ambiguous content fields. Exact MaterialRevision refs, FactPackItem citations/locators and declarations are validated alongside the payload and frozen into v5; an image key or citation in payload without its matching exact ref is invalid. The adapter owns canonicalize/validate, while the server enforces schema/profile/compatibility and computes the hash. Package projections consume this frozen canonical payload, never re-run adaptation.

## Risks / Trade-offs

- [Existing channel-bound Master semantics bleed into neutral flow] → Explicit source-only null-channel path and regression of v4 behavior before enabling v5.
- [Multiple target profiles or adapter updates silently retarget a variant] → Pin version/config hashes and require a new variant revision; preserve old approved history.
- [Cross-channel v5 authorization is rejected by the legacy Unit-channel gate or admits a mismatched account] → Dispatch on Candidate schema; compare v5 target channel/form to the frozen Variant while retaining pinned identity/account and verified remote-action checks.
- [Suggested or model-produced claims exceed evidence] → Mark unsupported facts as incomplete, require exact Fact Boundary refs, and save only after explicit acceptance.
- [A package or publisher edits approved content] → Build from frozen v5 manifest and exact bytes; block unsafe live rights, never rewrite at delivery.
- [Migration downgrade would lose v5 history] → Additive nullable link and new tables; refuse downgrade while v5-linked rows exist, rehearse only on isolated SQLite/PostgreSQL.
- [Matrix/Variant UI inflates common routes] → Lazy module boundary and FE-P1 import-graph budget gate.

## Migration Plan

After F6D acceptance and independent implementation review, inspect the actual Alembic head and models. F6D task 4.5 is the documented handoff of real Provider/rights/redaction obligations to F7; F7 Provider implementation is not an F6E prerequisite. Add tables for variant revisions/refs/checks plus nullable `content_asset.channel_variant_revision_id`, with foreign keys, bounded values, indexes, unique CAS/idempotency keys and a data-safe downgrade preflight. No historical backfill. Implement adapter/currentness before v5 builder, then schema dispatch, UI and isolated browser acceptance. Run isolated SQLite up/down/up and PostgreSQL-compatible DDL/rollback checks; never run a production migration under this change's specification approval.

## Open Questions

No product choice is required for specification review. Exact current channel/profile availability and schema/migration details must be rechecked on the F6D-complete base before apply. If that audit reveals a destructive migration, an unplanned durable business object or a safety-boundary reduction, stop and revise the proposal rather than proceeding.

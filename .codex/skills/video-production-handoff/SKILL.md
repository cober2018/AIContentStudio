# Video production handoff

Use the user-authorized project, unit, execution ID and package hash. The platform owns script, versions and acceptance; Resolve owns the main timeline; AE supplies requested compositions. Website video is external work, API images remain native generation.

## Read and claim

1. Use the configured local AIContentStudio creative MCP: get_execution/get_package/get_context. Confirm scope, current source, package hash, exact executor and state. Never substitute the workspace-reading C2C connector for the creative execution MCP.
2. A prepared task is not running. Claim once with the expected revision and frozen executor, materialize only authorized inputs, then start. Read the current revision after each mutation; do not overwrite a conflict. Use the returned input manifest and this execution's private workspace; no arbitrary files, cookies or credentials.
3. If unknown or possibly dispatched, inspect the original website/tool operation and use reconcile_unknown with genuine observation evidence. Do not regenerate, restart editing or switch provider to escape uncertainty. Quota remaining does not reset the task's single-submit budget.

## Website clip branch

First create/upload/select the shot image through the existing platform image flow, inspect the actual image, and obtain explicit human confirmation of that exact MaterialRevision before saving it as the shot reference. Library acceptance alone is not shot selection. After the image is confirmed and saved, inspect that image and author a distinct video motion/camera prompt describing retained elements, movement, camera and pacing. Do not reuse an image-generation description as a confirmed video prompt. Explicitly confirm and save video.shot-production.v2 with prompt_reference {revision_id, content_hash} matching the selected image. Editing the prompt invalidates confirmation; replacing the image retains the old prompt as stale until inspected, reviewed and explicitly confirmed again. Do not silently restamp a stale prompt or select an image on the human's behalf.

Read package.web_video: shot_id, frozen script/prompt/hash, provider, mode, reference MaterialRevision/hash, aspect, generation duration, use duration and audio intent. New website tasks require the saved image, matching prompt_reference and image_to_video mode. Download the exact authorized image through GET /api/v1/content-projects/{project_id}/units/{unit_id}/web-video-reference-images/{revision_id}?content_hash={sha256}&package_id={package_id}, which rechecks live rights and the frozen package, or materialize it through the scoped creative MCP; verify its content hash and send no credentials or base64 media in the brief. Prepare only manual website tasks. Give the user the frozen copyable brief and authorized reference file; the user pastes it into Grok/Gemini, generates, downloads and returns the original MP4. Do not operate website browsers, submit generations, poll or download for the user. Waiting for a file is an honest pending handoff, never a completed clip.

Use CLI REST or the creative MCP for all platform operations; never click the platform in a browser. Upload a returned file to its exact manual execution using the existing authorized multipart route and current expected_revision, role clip, index 1, video/mp4 and truthful metadata. Read back its hash and state. Preview/review and explicitly delegated acceptance are separate from upload; no automatic Master binding. Do not impersonate a human executor through agent claim/start MCP calls.

Preserve historic v1 text/image tasks, exact idempotent replays, playback, returns and explicit manual takeover; do not create new tasks from v1 as a workaround. Preserve historic agent website tasks/results. Manual takeover is explicit and allowed only for proven not_dispatched work; active/unknown work must first be reconciled from actual evidence. Never regenerate to escape uncertainty. Manual uploads use the same frozen shot and output validation.

## Product work

For unified product image-to-clip direction, use [product-video-material-director](../product-video-material-director/SKILL.md) with selected method versions and the contracts below.

When the frozen brief contains product_context, keep its original SKU/source/material revisions and selected Persona style. Product methods must have been chosen before the first generation Run, not first added after writing the script. For selected product methods use the exact method_card_text embedded in the frozen versioned instruction and verify its UTF-8 SHA256 against method_card_sha256. The method_card path is provenance only; never reload its mutable local file as execution guidance. A legacy frozen instruction without embedded card content uses only its already frozen text; adding a newer card requires an explicit new method revision and task. Ordinary capability instructions are not JSX or deterministic config patches. Do not read all candidate methods by default.

A single front photograph supports front-view framing, zoom and planar motion; it does not prove a backside or a 360-degree product. Check actual reference-input support before requesting reference-preserving generation. If unavailable, retain original pixels through real capture or native compositing; textual image mention is not a reference upload. Keep the original photo as identity truth rather than chaining only generated images. Physical product, apparel and software UI recipes have different applicability.

Verified prices and conditions come from the frozen product brief, not method arguments. An unknown deadline remains absent; no wall-clock countdown in a static video. Product-offer motion may be skipped without stopping feature content. Keep semantic narration edits ahead of beat sync; music/no-music follows the task. Return actual native operation and review evidence with the existing output contract.

## Professional edit branch

When the package contains `production_methods`, use its frozen stage manifest. After claiming, call `use_capability` with stage, execution ID, current expected revision and exact executor to load each stage being performed; retain the returned hashes and receipt. Only apply the enabled methods returned for that stage, in their recorded order and with their frozen parameters. Disabled and not-applicable IDs are not instructions. Explicitly empty/off stages use no optional creative Skill; unconfigured legacy stages retain the existing behavior. Identity, knowledge, evidence and technical output contracts remain active. Do not read an entire candidate collection or silently substitute a globally installed creative Skill. A delivery receipt proves instructions reached the executor; record actual decisions and outputs separately.

For native AE/Resolve operations, read [native execution notes](references/native-execution.md). These cover transport, timing and media correctness, and remain applicable when optional creative methods are off. The [method candidate inventory](references/production-methods.json) and [licenses](references/THIRD_PARTY_NOTICES.md) are selection resources, not automatically loaded creative instructions.

Read director.postproduction and all exact assets, narration/subtitles, shot use ranges, frame rate/resolution, audio intent, AE shot IDs and parent feedback. If required media is missing, report the precise gap. Use only the task's project; preserve unrelated application projects and global settings.

Create the Resolve main timeline. Narration drives timing; trim source clips to their intended use ranges. Mute generated clip sound unless the frozen shot explicitly keeps it. For requested AE work, read every ae_compositions entry independently: shot_id, role_id, duration_ms, resolution, fps and alpha_required. Use those exact per-composition parameters, even when they differ from the main timeline or other compositions. When alpha_required is true, choose a contract-allowed MOV codec/pixel format preserving alpha and verify the rendered alpha channel. Render each intermediate under its exact role and import it into Resolve. No requested AE work means skip AE.

Return rough_cut or final MP4 according to phase; resolve_project as application/x-resolve-project; edit_manifest as application/json; subtitles as application/x-subrip when required; and ae_project plus each ae_compositions entry's role_id when the contract requires AE. Use the exact frozen output role IDs/MIME/limits, never guessed filenames as proof.

The edit_manifest schema is video.edit-manifest.v1. Include source_master_revision_id/source_payload_hash, phase, fps, resolution; assets with exact material_revision_id/content_hash and authorized inputs/<filename> relative_path; timeline items with shot_id/material_revision_id/start_ms/end_ms/trim_start_ms/trim_end_ms/audio_intent and composition_role matching the exact ae_compositions role_id for each AE shot; output_hashes for all required roles except the manifest itself. Record project_reopen.resolve and, when used, project_reopen.ae with verified, missing_media=0, tool_version and observation_hash from actual reopen observations. Fully reopen the returned projects, check the timeline and media dependencies, and hash the genuine observation record. Preserve dependency files; do not clean a folder needed to reopen the project. This is a local workstation handoff: keep every exact input and intermediate in the preserved execution workspace, list their relative paths, and return its accessible work_root with the engineering artifacts. Do not claim a portable colleague handoff or a self-contained archive unless such a bundle was actually produced and reopened. Claims in the manifest are executor evidence, not proof that the platform invoked the tools itself.

## Feedback and completion

Feedback identifies an exact rough-cut output ID/hash and timecode. An unaccepted output can be rejected and replaced with a higher attempt. An accepted execution stays terminal: the user saves feedback/parent references in a new current Master and prepares a new refinement/final execution. Before editing, verify frozen parent_output_id, parent_output_hash and parent_material_revision_id against the accepted parent output. Include those exact parent references in the final handoff receipt, together with the new source Master ID/hash and execution ID. Do not edit the accepted task in place or claim a new Master exists without readback.

Submit every required artifact, check returned hashes/state and request review. Result-ready is not accepted. Human or explicitly delegated authorized product review happens separately; this Skill does not grant permission to accept outputs, save Master, approve or publish. Record the real page/tool readbacks and remaining blockers. A script, URL, project filename or generated plan is never a completed video.

## Concrete platform contracts

Connection details and the configured local creative MCP are documented in [CREATIVE_EXECUTION_MCP.md](../../../docs/CREATIVE_EXECUTION_MCP.md). Discover the current server tools/inputSchema rather than assuming a connector prefix. Never put its bearer secret in a prompt or receipt. Read the exact runtime tool schema before mutation.

All MCP inputs identify project_id and unit_id. get_execution adds execution_id; get_package adds package_id. Mutations add execution_id, expected_revision and executor_kind/executor_key/executor_version from the frozen execution. materialize_inputs optionally adds the exact material_revision_ids. submit_output adds role_id, output_index (the first required clip is index 1), relative_path under outputs/, mime_type and SHA256 content_hash. Output roles/count/MIME/max_bytes are at package.output_contract.roles; effective large-file limits are at package.output_contract.media_transfer_policy. Read these fields rather than reconstructing a contract.

reconcile_unknown additionally requires observation_hash, summary, resolution and dispatch_certainty. The current resolutions are in_progress, blocked, result_ready or failed_before_dispatch; certainty is confirmed_dispatched or not_dispatched. Use failed_before_dispatch only with evidence proving nothing was sent. Evidence hashes use SHA256 of the preserved UTF-8 observation record; preserve that exact record for review. A 409 means reread the original execution and reconcile the competing change; never guess its next revision or resend automatically.

The user-facing feedback entry remains project → content matrix → video unit → Director workspace → shot material/edit handoff. Codex uses only authorized CLI REST/MCP to save timecoded feedback/parent references in a new Master and prepare the next edit task. The server preparation routes below reuse the saved source and return execution/package/instructions: POST /api/v1/content-projects/{project_id}/units/{unit_id}/web-video-executions/prepare takes source_master_revision_id, shot_id, execution_mode and idempotency_key; video-edit-executions/prepare takes source_master_revision_id and idempotency_key. Web execution_mode defaults to manual; new codex web tasks are rejected. Historic idempotent calls remain readable. For manual file return use POST /api/v1/content-projects/{project_id}/units/{unit_id}/creative-executions/{execution_id}/uploads. Follow the current route multipart schema and permissions. These routes do not grant acceptance or Master-write authority by themselves.

In the manifest, resolution is the frozen two-integer [width,height] pair, fps is the frozen integer, output_hashes is an object mapping each required non-manifest role ID to the actual SHA256 of its submitted file. assets and timeline are arrays. project_reopen is an object keyed resolve and optionally ae; each observation has verified=true, missing_media=0, tool_version and observation_hash. Exact validation is in app/services/web_video_handoff.py (validate_edit_manifest and validate_edit_output_hashes); read those functions only if a contract mismatch remains. Do not invent alternate metadata names. If a requested trim does not specify the intended result, inspect existing feedback and ask one clarification before choosing how much content to remove.

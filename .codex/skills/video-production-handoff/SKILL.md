# Video production handoff

Use the user-authorized project, unit, execution ID and package hash. The platform owns script, versions and acceptance; Resolve owns the main timeline; AE supplies requested compositions. Website video is external work, API images remain native generation.

## Video chain: you lead, the platform records

For a whole video (e.g. 「做海底光缆的视频」) you make every creative decision; the platform calls no model. Articles follow the page switch (平台模型 or 第三方模型, see article-writing); images keep the platform's own abilities. Three stops wait for the user on the page; continue only after approval and treat notes as the next version.

1. `get_video_brief`: brief, facts, the source article, voice settings, library (外部 / 通用 / this project) and the current master. Write the 导演稿 yourself as a full `video.master.v2`: shots with `board` {message, visual, camera (fixed/push_in/pull_out/follow/orbit/pan), speaker, sound, notes, material_request} and `script.blocks`. `material_request` tells the user what footage to look for: what the picture must show, shot size, length, real footage or graphic, orientation. Keep one idea per shot, vary shot size and camera, and avoid repeating the same picture. Before choosing editing techniques read craft-resolve `choose.md`: plain cuts on the voice rhythm by default, a technique only for a named problem, and for each shot that uses one write in `notes` `手法：<entry>/<section>（试用 if trial）— 解决：<problem>`. `save_director_draft`, give the user the review link, then **stop**.
2. `get_video_decision`. Notes → a new 导演稿 and stop again. Approved → read the brief again for files the user added, match them to rows, and cover the rest yourself: library → `start_material_match` + `accept_material_candidate` → `generate_video_image` → AE templates. You pick every shot's material (`set_shot_materials`). Say in the receipt which rows came from the user and which you found or made. A material nearly every video could use (effect, transition, texture, common BGM / sound effect) goes to 通用素材库 on the Mac with `file_as_common`; say so in the receipt. Project-specific material stays with the project.
3. `generate_video_voiceover` (saved MiniMax settings; shot timing follows the voice).4. `prepare_video_edit` phase `rough_cut` with the shots that need AE. Work the task in DaVinci Resolve (cut, colour, sound, export) and After Effects (titles, captions, packaging, effects) as below; ffmpeg only for checks and container fixes. Submit → **小样**, request review, **stop**.
5. Notes on the 小样 → fix and submit a new 小样. Approved → `prepare_video_edit` phase `final`: 排版 (caption and title layout, packaging graphics, colour and sound polish) on top of the approved 小样, export → **成片**, request review, **stop**.

Cloning a reference video (the user attached one, or `brief.reference` is set): run `analyze_reference_video` with the library video, poll `get_reference_video` until `done`, then read the grid images and `transcript.json` / `cuts.json` it lists and follow `studio.video.reference-breakdown`: whole-piece analysis, timeline and shooting list → `save_reference_breakdown`, then the 导演稿 for this work with the reference's structure and rhythm, its own product and wording, and `board.source_kind` (shoot / product_image / generated / ae_template / library) on every shot. Certificates, hospitals and ingredient claims in the reference go into `brand_material` as needing the brand's real material; never copy or generate them. The reference footage and its watermark never enter the cut. People shots get `board.attitude` written with `studio.video.prompt-direction` (attitude and who they speak to first, one or two decisive reactions; first-frame stills in four parts: capture / person / action and camera / setting). After approval, product works can call `generate_storyboard_grid` for consistent people / scene first frames; its cells are candidates, never adopted for the user.

The edit follows the 导演稿: if picture content must change, save a new 导演稿 first. List the details the 导演稿 did not specify (trim points, move timing, caption placement) and the credits of web materials in the edit receipt.

## Read and claim

1. Use the configured local AIContentStudio creative MCP: get_execution/get_package/get_context. Confirm scope, current source, package hash, exact executor and state. Never substitute the workspace-reading C2C connector for the creative execution MCP.
2. A prepared task is not running. Claim once with the expected revision and frozen executor, materialize only authorized inputs, then start. Read the current revision after each mutation; do not overwrite a conflict. Use the returned input manifest and the task's folders; no arbitrary files, cookies or credentials. For video-chain edits materialize_inputs returns each input's original absolute `path` on the material drive (and `proxy_path` when the 代理素材 switch is on: edit with the proxy, export from the original), plus `work_dir` (`<项目>/工作/<作品>-<作品号>/任务<N>/`) and `export_dir` (`导出/小样` or `导出/成片`). Import originals into Resolve/AE directly from their paths, read-only, and never make working copies of source media. If the drive is not connected the platform refuses; tell the user.
3. If unknown or possibly dispatched, inspect the original website/tool operation and use reconcile_unknown with genuine observation evidence. Do not regenerate, restart editing or switch provider to escape uncertainty. Quota remaining does not reset the task's single-submit budget.

## Real product footage branch

For a saved real or mixed capture plan, read its script/task confirmations and the exact filming instructions before preparing work. The user shoots originals; no AI keyframe or completed voiceover is needed for this branch. Keep shooting order separate from edit order and each shot's planned use duration separate from raw duration.

Upload each original with actual media inspection, retain its material hash, source task Master and shot ID as a pending capture take. Inspect real frames and sound before recording usable time ranges or specific reshoot reasons. Ordinary phone quality is acceptable when the relevant product detail is clear. Close-ups do not establish durability or material composition. Review acceptance, source binding and edit placement are separate saved decisions. Keep previous takes and failed attempts.

Use only adopted usable ranges matching the current task. Director packages may contain rejected or pending raw references for traceability; their presence never authorizes including those ranges in the edit. If an upstream visual requirement changes, review the affected task; changing narration alone does not require filming again. Generate optional narration later and reconcile its actual duration with usable footage. Respect the existing sound, rhythm, color and optional AE handoff below.

## Website clip branch

First create/upload/select the shot image through the existing platform image flow, inspect the actual image, and obtain explicit human confirmation of that exact MaterialRevision before saving it as the shot reference. Library acceptance alone is not shot selection. After the image is confirmed and saved, inspect that image and author a distinct video motion/camera prompt describing retained elements, movement, camera and pacing. Do not reuse an image-generation description as a confirmed video prompt. Explicitly confirm and save video.shot-production.v2 with prompt_reference {revision_id, content_hash} matching the selected image. Editing the prompt invalidates confirmation; replacing the image retains the old prompt as stale until inspected, reviewed and explicitly confirmed again. Do not silently restamp a stale prompt or select an image on the human's behalf.

Read package.web_video: shot_id, frozen script/prompt/hash, provider, mode, reference MaterialRevision/hash, aspect, generation duration, use duration and audio intent. New website tasks require the saved image, matching prompt_reference and image_to_video mode. Download the exact authorized image through GET /api/v1/content-projects/{project_id}/units/{unit_id}/web-video-reference-images/{revision_id}?content_hash={sha256}&package_id={package_id}, which rechecks live rights and the frozen package, or materialize it through the scoped creative MCP; verify its content hash and send no credentials or base64 media in the brief. Prepare only manual website tasks. Give the user the frozen copyable brief and authorized reference file; the user pastes it into Grok/Gemini, generates, downloads and returns the original MP4. Do not operate website browsers, submit generations, poll or download for the user. Waiting for a file is an honest pending handoff, never a completed clip.

Use CLI REST or the creative MCP for all platform operations; never click the platform in a browser. Upload a returned file to its exact manual execution using the existing authorized multipart route and current expected_revision, role clip, index 1, video/mp4 and truthful metadata. Read back its hash and state. Preview/review and explicitly delegated acceptance are separate from upload; no automatic Master binding. Do not impersonate a human executor through agent claim/start MCP calls.

Preserve historic v1 text/image tasks, exact idempotent replays, playback, returns and explicit manual takeover; do not create new tasks from v1 as a workaround. Preserve historic agent website tasks/results. Manual takeover is explicit and allowed only for proven not_dispatched work; active/unknown work must first be reconciled from actual evidence. Never regenerate to escape uncertainty. Manual uploads use the same frozen shot and output validation.

Repository candidates guide this authorized preproduction work; they do not alter a frozen execution or prove a platform capability revision was published. Once an execution exists, its embedded method text remains authoritative as described below.

For an image-first request, show the sales idea, storyboard, asset gaps and actual per-shot candidate keyframes before video work. Each shot should answer a purchase question or add useful information, not merely change the crop. Do not silently turn insufficient source material into a single-photo slideshow and declare the sales creative accepted. An explicitly chosen limited static concept is still valid. Keep the original real photo in reference-based generation; identify generated detail or use scenes as illustrative. Save candidate versions/hashes and review observations, then wait for the user's exact image selection before authoring final motion prompts or generating video. Technical success, visual inspection and user creative approval are separate states; changed images need fresh selection. Do not impose this sample's shot count, color, wording or creative method selection on other tasks.

For sales work, check the seven business questions in the selected truth-brief card and use the selected story/shot cards to connect one buyer situation and one purchase reason to observable evidence. A roughly 30-second starting duration, five possible test formats and optional three-way expression comparison are planning aids, not universal gates. Separate AI scene illustration from actual demonstration, measurements, like-for-like comparisons and authorized feedback. Keep internal unit-economics inputs out of public copy unless explicitly intended, and keep missing costs or commercial terms unknown. Price, specifications, captions and purchase directions belong in verified postproduction overlays.

When the frozen brief contains product_context, keep its original SKU/source/material revisions and selected product style. Product work does not require a Persona; retain legacy frozen context without introducing a Persona dependency. Product methods must have been chosen before the first generation Run, not first added after writing the script. For selected product methods use the exact method_card_text embedded in the frozen versioned instruction and verify its UTF-8 SHA256 against method_card_sha256. The method_card path is provenance only; never reload its mutable local file as execution guidance. A legacy frozen instruction without embedded card content uses only its already frozen text; adding a newer card requires an explicit new method revision and task. Ordinary capability instructions are not JSX or deterministic config patches. Do not read all candidate methods by default.

A single front photograph supports front-view framing, zoom and planar motion; it does not prove a backside or a 360-degree product. Check actual reference-input support before requesting reference-preserving generation. If unavailable, retain original pixels through real capture or native compositing; textual image mention is not a reference upload. Keep the original photo as identity truth rather than chaining only generated images. Physical product, apparel and software UI recipes have different applicability.

Verified prices and conditions come from the frozen product brief, not method arguments. An unknown deadline remains absent; no wall-clock countdown in a static video. Product-offer motion may be skipped without stopping feature content. Keep semantic narration edits ahead of beat sync; music/no-music follows the task. Return actual native operation and review evidence with the existing output contract.

Read their index with `get_craft_skill` (pass the project and unit), then only the entry you need. These two are always readable. If required media is missing, report the precise gap. Use only the task's project; preserve unrelated application projects and global settings.

Create the Resolve main timeline. Narration drives timing; trim source clips to their intended use ranges. Mute generated clip sound unless the frozen shot explicitly keeps it. For requested AE work, read every ae_compositions entry independently: shot_id, role_id, duration_ms, resolution, fps and alpha_required. Use those exact per-composition parameters, even when they differ from the main timeline or other compositions. Render each intermediate under its exact role and import it into Resolve. No requested AE work means skip AE.

Return rough_cut or final MP4 according to phase; resolve_project as application/x-resolve-project; edit_manifest as application/json; subtitles as application/x-subrip when required; and ae_project plus each ae_compositions entry's role_id when the contract requires AE. Use the exact frozen output role IDs/MIME/limits, never guessed filenames as proof.

The edit_manifest schema is video.edit-manifest.v1. Include source_master_revision_id/source_payload_hash, phase, fps, resolution; assets with exact material_revision_id/content_hash and `path`, the original absolute path materialize_inputs returned; timeline items with shot_id/material_revision_id/start_ms/end_ms/trim_start_ms/trim_end_ms/audio_intent and composition_role matching the exact ae_compositions role_id for each AE shot; a shot cut from several clips gets one item per cut, each naming a material placed inside that shot on the Master timeline and its exact source range; output_hashes for all required roles except the manifest itself. Record project_reopen.resolve and, when used, project_reopen.ae with verified, missing_media=0, tool_version and observation_hash from actual reopen observations. Fully reopen the returned projects, check the timeline and media dependencies, and hash the genuine observation record. Preserve dependency files; do not clean a folder needed to reopen the project. This is a local workstation handoff: keep every intermediate (renders, AE shot renders, Resolve / AE projects, the manifest) in this task's work_dir, export the 小样 / 成片 straight into export_dir, and list those paths in the receipt. The platform removes unregistered files of older tasks of the same work when a newer 小样 comes back, and keeps only the approved 成片 task's folder. Do not claim a portable colleague handoff or a self-contained archive unless such a bundle was actually produced and reopened. Claims in the manifest are executor evidence, not proof that the platform invoked the tools itself.

## Feedback and completion

Feedback identifies an exact rough-cut output ID/hash and timecode. An unaccepted output can be rejected and replaced with a higher attempt. An accepted execution stays terminal: the user saves feedback/parent references in a new current Master and prepares a new refinement/final execution. Before editing, verify frozen parent_output_id, parent_output_hash and parent_material_revision_id against the accepted parent output. Include those exact parent references in the final handoff receipt, together with the new source Master ID/hash and execution ID. Do not edit the accepted task in place or claim a new Master exists without readback.

Submit every required artifact, check returned hashes/state and request review. Result-ready is not accepted. Human or explicitly delegated authorized product review happens separately; this Skill does not grant permission to accept outputs, save Master, approve or publish. Record the real page/tool readbacks and remaining blockers. A script, URL, project filename or generated plan is never a completed video.

## Concrete platform contracts

Connection details and the configured local creative MCP are documented in [CREATIVE_EXECUTION_MCP.md](../../../docs/CREATIVE_EXECUTION_MCP.md). Discover the current server tools/inputSchema rather than assuming a connector prefix. Never put its bearer secret in a prompt or receipt. Read the exact runtime tool schema before mutation.

All MCP inputs identify project_id and unit_id. get_execution adds execution_id; get_package adds package_id. Mutations add execution_id, expected_revision and executor_kind/executor_key/executor_version from the frozen execution. materialize_inputs optionally adds the exact material_revision_ids. submit_output adds role_id, output_index (the first required clip is index 1), mime_type, SHA256 content_hash and, for video-chain edits, `path`: the absolute path where the file was exported (rough_cut / final inside export_dir, every other role inside work_dir, no shortcuts). The platform checks and registers the file in place without copying, so do not change or move it afterwards; a changed file is refused at review with 文件已变化，请重新交付. Other executors give relative_path under outputs/. Output roles/count/MIME/max_bytes are at package.output_contract.roles; effective large-file limits are at package.output_contract.media_transfer_policy. Read these fields rather than reconstructing a contract.

reconcile_unknown additionally requires observation_hash, summary, resolution and dispatch_certainty. The current resolutions are in_progress, blocked, result_ready or failed_before_dispatch; certainty is confirmed_dispatched or not_dispatched. Use failed_before_dispatch only with evidence proving nothing was sent. Evidence hashes use SHA256 of the preserved UTF-8 observation record; preserve that exact record for review. A 409 means reread the original execution and reconcile the competing change; never guess its next revision or resend automatically.

The user-facing feedback entry remains project → content matrix → video unit → Director workspace → shot material/edit handoff. Codex uses only authorized CLI REST/MCP to save timecoded feedback/parent references in a new Master and prepare the next edit task. The server preparation routes below reuse the saved source and return execution/package/instructions: POST /api/v1/content-projects/{project_id}/units/{unit_id}/web-video-executions/prepare takes source_master_revision_id, shot_id, execution_mode and idempotency_key; video-edit-executions/prepare takes source_master_revision_id and idempotency_key. Web execution_mode defaults to manual; new codex web tasks are rejected. Historic idempotent calls remain readable. For manual file return use POST /api/v1/content-projects/{project_id}/units/{unit_id}/creative-executions/{execution_id}/uploads. Follow the current route multipart schema and permissions. These routes do not grant acceptance or Master-write authority by themselves.

In the manifest, resolution is the frozen two-integer [width,height] pair, fps is the frozen integer, output_hashes is an object mapping each required non-manifest role ID to the actual SHA256 of its submitted file. assets and timeline are arrays. project_reopen is an object keyed resolve and optionally ae; each observation has verified=true, missing_media=0, tool_version and observation_hash. Exact validation is in app/services/web_video_handoff.py (validate_edit_manifest and validate_edit_output_hashes); read those functions only if a contract mismatch remains. Do not invent alternate metadata names. If a requested trim does not specify the intended result, inspect existing feedback and ask one clarification before choosing how much content to remove.
